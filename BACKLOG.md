## P1 — release-bump вне install-source чекаута: круг двух валидаторов (REVIEWER-DEFAULT-SOL, 2026-09-01)

Реестр гейта и commit-гейт прогоняют проверку ИНСТАЛЛОВЫМ валидатором
(`itd_verification_loop` / `itd_review_cache`), который берёт
`methodologyVersion` из manifest'а СВОЕГО INSTALL_ROOT. Для release-bump
кандидата, готовящегося НЕ в install-source чекауте (worktree), квитанции
repo-валидатора несут новую версию, инсталлового — старую: каждая валидна
только у чеканившего. Repo-first (LPD-002 R2) покрывает только чекаут из
`~/.claude/.itd-install-source.json`. Обход в v1.102.0: релизная цепочка
целиком чеканилась инсталловым loop'ом + разовый флип провенанса на worktree
для commit-гейта (бэкап/восстановление). Корневой фикс — кандидат в юнит
вместе с «P1 ретро: repo-first для pre-push»: repo-first должен либо
принимать доверенный worktree того же репозитория, либо контекст не должен
включать версию из manifest'а валидатора.

**Наблюдение (31 раунд ревью, измерено):** чистых PASS три, то есть примерно

(битые типы, нечисловые версии, несериализуемые объекты, неполные политики).
Это отдельная модель угроз: файл лежит в репозитории под той же защитой, что и
читающий его код. Предмет пилота её не включал, поэтому класс выделен сюда.

**Дважды ревьюер потребовал отменить собственные прежние требования:**
- «запись не должна быть безлимитной» (pub2, r23) против «усечение
  противоречит хранению целиком» (r26);
- «отклонённый комментарий обязан повторяться» (r21) против «повтор раздувает
  карантин» (r26).
Оба разрешены НЕ выбором полюса, а конструкцией: предел закрывает вход в
канонический леджер, карантин хранит запись целиком, а размер обоих держит
ротация; счёт ведётся по различным личностям записи, поэтому повтор не
раздувает измерение. Приём записан как методологический: спор двух требований
решается контрактом, а не чередованием реализаций.

**Ложные находки последнего раунда (проверены по факту, не приняты):**
- «python в shell-heredoc, `__file__` не резолвится» — хук запускается
  диспетчером как файл: `hooks/codex-dispatch.py:144` -> `[sys.executable, str(script)]`;
- «имя счётчика расходится с замороженным контрактом» — имя файла счётчика
  не зафиксировано ни в одном контракте или доке (проверено поиском).

**Открытые пункты класса:** дедуп карантина под конкуренцией остаётся
предзаписью best-effort (измерение при этом точное); идемпотентность действует
в пределах текущего поколения; проверка документации сверяет словарь точно,
но не ловит новые значения, не попавшие ни в док, ни в legacyMapping.

## P1 — `sync-to-active.sh` и не-UTF-8 `settings.json` (выведен из INSTALL-HARDENING, 2026-08-29)

Шаг 5/6 читает `settings.json` без `encoding` и пишет обратно UTF-8. На
Windows-профиле с кириллическим путём (`C:/Users/Дмитрий/...`) файл лежит в
ANSI-кодировке -> `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xc4 in
position 868`, регистрация хуков молча не выполняется (замер 2026-08-29).

**Почему пункт открыт, а не закрыт в юните.** Две попытки формы «пробовать
кодировки по списку» отвергнуты независимым ревьюером на разных кандидатах:

- r3: `utf-8-sig` стоял перед `utf-8`, а он декодирует и BOM-less UTF-8 —
  каждый обычный файл получал НОВЫЙ BOM при записи.
- r5: `cp1251` перед `cp1252` — байты cp1252 (`é`) успешно декодируются как
  другие символы cp1251, ошибки нет, текст молча искажается.

Повтор ключа механизма в двух разных раундах — сигнал дефектной ФОРМЫ по
`.itd/STOP_RULE_POLICY.json`. Корень: однобайтовые кодировки декодируют почти
любые байты, поэтому перебор с `except UnicodeDecodeError` не может их
различить. Любая следующая перестановка порядка даст третью находку того же
класса.

**Формы-кандидаты для решения владельца** (нужен выбор ДО кода):
1. Fail-closed без транскодирования: не-UTF-8 файл не переписывается, шаг
   отказывает с путём/причиной/FIX. Крэш исчезает, авторегистрация хуков на
   таком хосте — нет.
2. То же + явный `--assume-encoding <name>`: транскодирование только по
   осознанному решению оператора.

Работа обеих попыток сохранена: `.itd-memory/p3-settings-encoding-attempt.patch`
(199 строк, включая 13 проверок сьюта). Не применять вслепую — форма отвергнута.

## P1 — иерархический unit-срез диффа без заголовка файла даёт ревьюеру ложные выводы (LPD-003-4 pub5, 2026-08-27; записано мандатом владельца)

Публикационный раунд pub5 юнита LPD-003-4 вернул BLOCKED с фактически ложной
находкой: «tests/verify_observed_token_telemetry.py импортирует только json,
cost_tracker_checks упадёт с NameError» — при том что на том же дереве импорты

шапку файла (импорты/константы) для каждого файла, чьи hunks попали в юнит,
либо дисклеймер «контекст неполон — NameError-класс выводов запрещён» (по
прецеденту BOUND_RANGE_FACTS из фикса v1.97.0). Цена дефекта измерена: один
ложный BLOCKED = сработавшее стоп-правило + решение владельца + лишний
producer-раунд.

## P1 — surface-growth treadmill: измеренный пробел правила остановки (LPD-003-3, 2026-08-25)

Замер живой серии ревью самого LPD-003-3 (сессия 2026-08-25): **13 вердиктов
BLOCKED подряд (r15-r35), 7 транспортных срывов между ними, ~23 реальные

**Пробел:** правило меряет повтор механизма, но не меряет поток на растущей
поверхности. Кандидат в расширение — второй критерий остановки: «механизмы
новые, но за последние K вердиктов все находки лежат в коде, добавленном ПОСЛЕ
старта серии, и поток стабилен -> терминал решения владельца
(SURFACE_TREADMILL)». Порог и форма — предмет отдельного юнита; данные серии
записаны в отчётах LPD003-3-r15..r35 и в HANDOFF-LPD003-3.md.

**Открытые находки r35** (останов по решению владельца, вариант C —
зафиксированы, не чинились):

  приёмки (activeFollowup ещё in_progress). Снять или закрыть при ledger-close

## P2 — скраббер ложно блокирует ревью на длинном дефисном идентификаторе (найдено REVIEWER-DEFAULT-SOL, 2026-08-31)

`contains_high_entropy_token` принял идентификатор критерия приёмки за
высокоэнтропийный токен и заблокировал ревью кандидата детерминированно, все
8 заходов продюсера:
`candidate diff contains sensitive material; review is blocked`. Секрета в
диффе не было — сработала эвристика энтропии на обычном kebab-case имени.

Обход в юните: идентификатор переставлен по сегментам (порядок слов в хвосте),
после чего проходит. Это ОБХОД, а не
починка: класс дефекта остаётся — любой достаточно длинный дефисный
идентификатор в дифффе может дать ложную блокировку, и диагностика не называет
ни файл, ни строку, ни причину, что стоило отдельного расследования.

Починка: детектор энтропии должен исключать токены, целиком состоящие из
словарных сегментов kebab-case, а отказ обязан называть файл, строку и
сработавший детектор (сейчас все три детектора дают одно и то же сообщение).
Оценка: S. Риск невмешательства: ложные блокировки публикации на ровном месте.

Точные значения идентификаторов НЕ приводятся в этой записи намеренно: первая
редакция пункта содержала проблемную строку буквально и сама воспроизводила
блокировку публикации. Это дополнительный симптом того же дефекта — описать
его в репозитории нельзя, не споткнувшись о него.
