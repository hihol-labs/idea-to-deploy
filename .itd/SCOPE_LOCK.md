# Scope Lock — R2 (LPD-002): гейт коммита в репо методологии судит кандидата кодом кандидата

## Current Task

Когда рабочий каталог — **сам репо методологии**, PreToolUse-гейт коммита
`hooks/check-review-before-commit.sh` загружает валидатор кэша ревью
`skills/review/scripts/itd_review_cache.py` **из этого репо**, а не из инсталла.
Для любого другого проекта поведение не меняется: валидатор берётся из инсталла,
как сейчас. Claim идёт riskTier **medium**: правка ограничена резолвом ОДНОГО
пути внутри одного хука, не меняет ни один ключ контекста кэша, ни модель
доверия, ни то, что считается успешным ревью. Второй пункт плана
`.itd-memory/LPD-002_UNIT_PLAN.json` (approved владельцем 2026-08-18), WIP=1.

## Корень (измерен, не предположен — retro 2026-08-18, сигнал E3/P3)

`CACHE_SCRIPT` (`hooks/check-review-before-commit.sh:23-26`) резолвится от
расположения САМОГО ХУКА: `Path(__file__).resolve().parents[1] / skills / review
/ scripts / itd_review_cache.py`. Хук зарегистрирован из инсталла
(`~/.claude/hooks/`), поэтому в репо методологии гейт грузит ИНСТАЛЛОВУЮ копию
валидатора. У валидатора `INSTALL_ROOT = Path(__file__).resolve().parents[3]`
(`skills/review/scripts/itd_review_cache.py:26`), а `methodologyVersion()`
(:206-226) читает `INSTALL_ROOT/.claude-plugin/plugin.json` — то есть версию
ИНСТАЛЛА. `/review` при этом пишет квитанцию валидатором ИЗ РЕПО (скиллы
резолвят скрипты repo-first), стало быть с версией РЕПО.

Следствие: как только версия в дереве отличается от установленной — а на
релизном коммите это по построению так, бамп версии и есть содержание
коммита, — `methodologyVersion` записи не совпадает с `methodologyVersion`
проверки, `record_matches` даёт промах, и гейт **ложно блокирует коммит**,
для которого ревью реально пройдено. Замер: ~25 мин и два лишних перечеканенных
маршрута на релиз v1.98.0.

Класс дефекта: **кандидата судят кодом, который не является кандидатом.** Тот же
класс, что закрывали в S9 (committed-head claim) — здесь он остался в хуке.

## Поправка (2026-08-18, находка независимого чекера)

Первая редакция детекта опиралась на имя плагина в манифесте рабочего каталога.
Чекер воспроизвёл живьём: имя **самопровозглашённое**, поэтому любой git-репо,
положив два файла (манифест с `name: idea-to-deploy` и всегда-true валидатор по
каноническому пути), отключал коммит-гейт и получал исполнение своего
python-кода внутри процесса хука. До R2 гейт исполнял только код инсталла — то
есть первая редакция была расширением поверхности доверия, а не сужением.

Якорь перенесён туда, куда кандидат писать не может: инсталл. `sync-to-active.sh`
запоминает checkout, из которого собран, и гейт грузит валидатор из репо только
для ЭТОГО пути. Нет провенанса (свежий клон, инсталл без синка) — прежнее
поведение, инсталловый валидатор. Проверка имени плагина и совпадение корня
оставлены как второй и третий рубеж.

## Принцип

Repo-first — это **сужение**, а не ослабление: гейт по-прежнему требует полного
совпадения exact-context и по-прежнему fail-closed при любой ошибке. Меняется
ровно одно — ЧЕЙ экземпляр валидатора считает контекст: в репо методологии это
код кандидата, во всех остальных проектах — инсталла. Детект намеренно узкий
(манифест в корне git + имя плагина + совпадение корня), потому что широкий
детект («есть файл по такому пути») превращает гейт в то, что произвольный
проект может переопределить своим файлом — это и пинится канарейкой изоляции.
