# Review broker deployment

The production boundary is an always-on HTTPS service controlled by the
dedicated GitHub App. Candidate code is never checked out or executed here.

## Secret boundary

The free-primary service uses five distinct files:

- GitHub App private key generated by the App registration;
- GitHub webhook secret generated by the App registration;
- public maker-provenance keyring;
- public free-review producer keyring;
- a broker-owned raw 32-byte Ed25519 key that countersigns live phase two.

No OpenAI API key is required or mounted for this route. The OpenAI key
previously disclosed in chat is ineligible. A rotated service-account key may be added
only after separate explicit consent by setting both the bounded key file and
`ITD_PAID_REVIEW_CONSENT=approved`; it is never an automatic fallback.

For a production Linux host, prefer the systemd unit and
`systemd-creds encrypt` so secret material is exposed only through
`$CREDENTIALS_DIRECTORY` to the unprivileged `itd-review` process. The Compose
file is a local/staging parity path; it mounts secrets as read-only files,
binds HTTP only to loopback, and expects Caddy or another TLS proxy in front.

## Build and staging probe

From the repository root:

```text
docker build -f services/review_broker/Dockerfile \
  -t itd-review-broker:local .
docker compose \
  -f services/review_broker/deploy/compose.yaml \
  --env-file services/review_broker/deploy/review-broker.env \
  config
```

Create `services/review_broker/deploy/runtime/` outside Git tracking with
directories owned by UID/GID `65532`; never reuse a developer credential.
The process intentionally refuses `OPENAI_API_KEY` in its environment.

The producer submits its signed phase-one envelope and exact live coordinates
to `POST /free-review`. The broker verifies the producer key, creates an
App-owned in-progress Check Run, re-fetches the PR head tree, head parent,
test-merge parents, and Check identity through the installation token, then
persists the phase-two receipt before publishing success. Any finding,
unavailable model, stale coordinate, forged signer, or persistence failure
keeps the Check fail-closed.

Each free-review keyring entry is scoped to one repository, enrollment App,
producer identity, and a closed non-empty model allowlist for every provider in
the mandatory route. A minimal entry is:

```json
{
  "free-reviewer-2026-08": {
    "publicKey": "<base64url-raw-ed25519-public-key>",
    "repository": "hihol-labs/example",
    "appIntegrationId": 424242,
    "producerId": "itd-free-reviewer-producer-v1",
    "reviewerModels": {
      "openai-subscription": ["gpt-5.6-sol", "gpt-5.6-terra"]
    }
  }
}
```

Prepared free-review evidence is reconciled on broker startup. If GitHub
accepted the success PATCH but local finalization was interrupted, recovery
observes the same App-owned Check Run and finalizes the existing receipt; it
does not create or charge for another review.

## Systemd host bootstrap

Install the reviewed release under `/opt/itd-review-broker`, then create the
exact Python runtime referenced by the unit and install only the locked
artifacts:

```text
python3 -m venv /opt/itd-review-broker/venv
/opt/itd-review-broker/venv/bin/python -m pip install \
  --only-binary=:all: --require-hashes \
  -r /opt/itd-review-broker/services/review_broker/requirements.lock
```

Verify the unit file against that release before enabling it. Start the
service only after the credential files and dedicated GitHub App client ID are
installed.

## GitHub App bootstrap profiles

`local-submission` does not create an App. For `self-hosted-app`, create a
private App under the repository owner's user/organization account, or choose
public visibility when installations will span other owners. For
`managed-app`, the service operator creates one public App. In every case the
repository owner explicitly chooses where to install it, and merge/deploy stay
with that owner or a separate CI identity.

Create an App only after the broker has a stable public HTTPS origin. Preview a
self-hosted organization App first:

```text
python scripts/itd_github_app_manifest.py \
  --owner example-org \
  --account-type organization \
  --profile self-hosted-app \
  --visibility private \
  --broker-url https://review.example.org \
  --output-dir /secure/itd-review-app \
  --plan
```

Then start the loopback callback and open the printed local URL in the browser:

```text
python scripts/itd_github_app_manifest.py \
  --owner example-org \
  --account-type organization \
  --profile self-hosted-app \
  --visibility private \
  --broker-url https://review.example.org \
  --output-dir /secure/itd-review-app \
  --serve --apply
```

For a managed App, use `--profile managed-app`; it resolves to public visibility
and rejects `--visibility private`. A personal self-hosted App uses
`--account-type user`.

The manifest requests only `checks:write`, `contents:read`,
`pull_requests:read`, and metadata access, and subscribes only to
`pull_request` and `merge_group`. It writes the RSA private key, webhook
secret, and non-secret registration record outside the repository with mode
`0600`; the generated OAuth client secret is deliberately discarded. Install
the App only on controlled repositories.

After the App has emitted its first Check Run, apply the App-bound ruleset and
observe the exact live enrollment:

```text
itd gate enrollment \
  --repository example-org/example \
  --scope organization \
  --ruleset-id <active-ruleset-id> \
  --app-id <dedicated-app-id> \
  --app-slug <dedicated-app-slug> \
  --workflow-repository-id <itd-release-repository-id> \
  --workflow-sha <pinned-itd-release-sha> \
  --output /secure/example-enrollment.json

itd gate enrollment \
  --repository example-org/example \
  --scope organization \
  --ruleset-id <active-ruleset-id> \
  --app-id <dedicated-app-id> \
  --app-slug <dedicated-app-slug> \
  --workflow-repository-id <itd-release-repository-id> \
  --workflow-sha <pinned-itd-release-sha> \
  --output /secure/example-enrollment.json \
  --apply
```

The second command persists only metadata observed from GitHub. Feed that
receipt to the broker operator; do not hand-author or edit it.

## Enrollment operator

Preview and apply a public provenance record:

```text
python -m services.review_broker.operator keyring-add \
  --keyring /secure/provenance-keyring.json \
  --record /secure/repository-public-key.json

python -m services.review_broker.operator keyring-add \
  --keyring /secure/provenance-keyring.json \
  --record /secure/repository-public-key.json \
  --apply
```

Restart the broker after a new keyring entry. Then preview/apply the
schema-validated live enrollment receipt:

```text
python -m services.review_broker.operator enroll \
  --database /var/lib/itd-review-broker/review-broker.sqlite3 \
  --keyring /secure/provenance-keyring.json \
  --receipt /secure/enrollment-receipt.json

python -m services.review_broker.operator enroll \
  --database /var/lib/itd-review-broker/review-broker.sqlite3 \
  --keyring /secure/provenance-keyring.json \
  --receipt /secure/enrollment-receipt.json \
  --apply
```

An active enrollment is immutable. App or ruleset rotation requires an
explicit disable/rotation procedure and a freshly observed receipt; editing
the database is never supported.

## Readiness and exposure

Expose only the TLS proxy. `/healthz` proves the process is alive. A repository
is gate-ready only when:

```text
GET /readyz?repository=<owner/repo>&appId=<dedicated-app-id>
```

returns HTTP 200 with the exact policy SHA, reviewer routes, positive budget
admission, active enrollment receipt, and matching public provenance key.
Reverse-proxy access logs must not include request bodies or authorization
headers. Back up the SQLite database atomically (SQLite backup API or a stopped
service copy), test restoration, and retain the encrypted credentials
separately.
