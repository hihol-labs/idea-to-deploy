# Completion Gate — полная механика (topic-док)

> Источник истины по ПОВЕДЕНИЮ — код: `hooks/completion-signals.sh`,
> `hooks/completion-gate.sh`, `hooks/completion-stop.sh`, `hooks/completion_lib.py`
> (+ пайп-тесты в `hooks/README.md`, функциональные — `tests/verify_completion_*.py`).
> Этот док — справочник для человека и для агента, отлаживающего гейт. В
> глобальном `CLAUDE.md` (блок `docs/templates/global-claude-md.md`) остаётся
> только компактное правило с указателем сюда — по принципу «часто нужное под
> рукой, иногда нужное — в topic-док» (v1.73.0, дедуп прозы и кода).

Фича завершена = **сквозная верификация пройдена**, а не «код написан». Суждение
о завершении выносит НЕ агент по своей уверенности, а независимый harness-гейт по
объективным runtime-сигналам (леджер `.claude/completion/signals.jsonl`, вердикт
`.claude/completion/completion.json`). Это вендор-нейтральный контракт: сигналы и
вердикт — JSON-файлы в репо, а хуки (`completion-signals`, `completion-gate`,
`completion-stop`) лишь ТРАНСПОРТИРУЮТ его. Нет леджера → гейт деградирует в
advisory, а не в ложное «all green» (best-effort invariant).

## Трёхслойная лестница (дёшево → дорого, переход только после зелёного)

Порядок обязателен — не переходи на следующий слой, пока предыдущий не зелёный
(правило исполняется `compute_verdict`, не на словах):

- **L1 — Синтаксис и статика** (дёшево, мало информации, но обязателен): линт,
  типы, сборка (`tsc`, `eslint`, `ruff`, `next build`, `cargo check`…). Сначала
  «написать слова правильно».
- **L2 — Runtime-поведение** (основное доказательство): **тесты реально прогнаны
  и зелёные**, приложение стартует, критические пути отрабатывают. Правило
  жёсткое: **тесты зелёные — иначе не done**. «Написать тест» ≠ «прогнать тест».
  Не переходи к L2, пока L1 красный.
- **L3 — Системное подтверждение** (дорого, последняя линия): e2e/smoke,
  интеграция, симуляция пользовательского сценария. Недостаточно «работает» —
  должно работать ПРАВИЛЬНО. Не переходи к L3, пока L2 красный.

## Runtime-сигналы (что собирается автоматически)

`completion-signals` (PostToolUse) классифицирует каждый Bash-вызов в сигнал:
`static`(L1) / `test_run`(L2) / `app_start`(L3) / `side_effect`(миграции, записи
в БД) / `cleanup`(удаление временных ресурсов). Чек-лист доказательства
завершения — это те же сигналы: **прошли ли тесты; стартовало ли приложение;
корректны ли записи в БД и другие побочные эффекты; очищены ли временные
ресурсы**. Проекты без юнит-тестов подставляют свой L2-эквивалент через
`.claude/completion/config.json` (`l2_evidence_patterns`) — команда-доказательство
поведения засчитывается как `test_run`.

## Красные пометки (WHY + FIX, гарантированы контрактом)

Любой сбой проверки оформляется как пометка учителя, а не «просто крест»:
`FAILED: <что> | WHY: <сигнал> | FIX: <конкретное действие> | FILE: <путь>`.
`completion-signals` возвращает такую пометку модели в момент провала теста/
сборки (self-correction без ожидания коммита); таблица `FIX_HINTS` в
`completion_lib.py` даёт действие по классу ошибки (5xx→env, `ECONNREFUSED`→подними
сервис, `TS####`→типы, `relation … does not exist`→миграция, …).

## Механика вето и деградации

- `completion-gate` (PreToolUse на `git commit`, где в staged-диффе есть **код**):
  слой в FAIL или «тесты есть, но не прогнаны» → **вето** (deny, коммит стоп);
  нет ни одного сигнала за сессию → **деградация** в advisory (коммит идёт, но с
  напоминанием); слои зелёные → пропуск.
- `completion-stop` (Stop): при грязном по коду дереве и не-зелёном вердикте —
  мягкое напоминание, никогда не блокирует.
- `/session-save --close`: явная граница завершения сессии. Runner
  `.itd/itd_hygiene.py close` требует одновременно зелёные verification/startup
  checks, свежий quality ledger, отсутствие debug-маркеров, manifest-cleanup и
  чистый `git status`. Это hard exit-код только по явному намерению закрыть
  сессию; обычный Stop остаётся soft.
- **Осознанный обход**: `COMPLETION_BYPASS: <причина>` (или `SKILL_BYPASS:`) в
  поле description Bash-вызова коммита. Причина обязательна и исключение
  записывается в `.itd-memory/events.jsonl`. Kill switch
  `ITD_COMPLETION_GATE=0` также требует `ITD_COMPLETION_BYPASS_REASON`; без неё
  strict/high-risk commit остаётся заблокирован.
  (гейт), `ITD_COMPLETION_STOP=0` (Stop), `ITD_COMPLETION_SIGNALS=0` (сбор).

Гейт узкий (срабатывает только на коммитах с исходным кодом) и деградирующий —
это Definition of Done через объективные сигналы, а не алармизм.

## Запись прогона: красный, вытесненный более поздним зеленым (COMPLETION-SUPERSEDE-1, 2026-10-02)

Гейт знает прогон по тексту Bash-вызова: красный одноразовой команды (RED-first в копии до фикса,
прогон мутации `/test` Step 5.5, тот же оракул за другим пайпом) не вытесняется зеленым прогоном того
же оракула под другим текстом. Идентичность прогона дает запись раннера, а не разбор текста команды:

    ITD_RUN_RECORD=1 sh skills/_shared/itd_py.sh tests/verify_x.py [args]

- **Раннер.** С `ITD_RUN_RECORD=1` запуск идет через `skills/_shared/itd_run_record.py`: та же команда
  тем же интерпретатором, код выхода возвращается без изменений. После завершения
  пишется запись `<каталог записей>/<id>.json` `{id, script, args, cwd, rc, isolated, python, lines}`
  (`script` - путь относительно каталога прогона, `lines` - хвост вывода прогона: до 400 строк на
  поток) и одна строка `ITD-RUN <id>` в stderr. Содержимое stdout и stderr обернутой команды
  передается дальше без изменений, но каждый поток идет через свой пайп: взаимный порядок двух потоков
  при `2>&1` и `isatty` не сохраняются. SIGTERM/SIGHUP раннера пересылаются обернутой команде. Каталог записей -
  `~/.local/state/itd/runs` (права 0700, файлы 0600: в записи аргументы и хвост вывода);
  несопоставленные записи старше недели удаляются. `ITD_RUN_RECORD_DIR`
  переносит каталог, только если задана в окружении и раннера, и хука (служебная настройка оракула):
  заданная в одном Bash-вызове, она хуку не видна, запись не найдется и прогон судится как без записи.
  Без переменной запуск побайтно прежний. Вложенные запуски раннера не записываются. Не удалось
  записать - строки `ITD-RUN` нет. Прогоны без скрипта (`-c`, `-m`) не записываются.
- **Привязка.** Хук прикладывает запись к сигналу (`run`), только если в выводе, который он наблюдал
  сам, ровно одна строка `ITD-RUN <id>`, файл записи существует и корректен, а КАЖДАЯ непустая строка
  вывода - посимвольно строка самого прогона (не чаще, чем прогон ее напечатал) либо одно эхо кода выхода, равное
  записанному. Порядок строк не важен (stdout и stderr вызова приходят раздельно). Вывод любой другой
  команды того же вызова, до или после прогона, отвязывает запись. Файл записи удаляется первым вызовом, показавшим ее id, даже если привязка не состоялась: повтор того же id
  (например, `cat` старого лога) записи уже не найдет. Исход сигнала считается как раньше.
- **Суждение** (`counted_signals`). Красный сигнал с записью (`rc != 0`) не учитывается, когда
  ПОСЛЕДНЯЯ запись того же вызова (скрипт, аргументы, режим `--itd-isolated`, интерпретатор, слой
  сигнала) - сигнал с исходом pass, `rc == 0`, каталог прогона
  которого - корень проекта, на текущем HEAD (у проекта есть HEAD, и зеленый сигнал называет тот же). Снятие только убирает красный: pass слоя дает сам зеленый
  прогон. Так судят и `compute_verdict`, и строгий путь гейта.

Блокирует как раньше: красный без записи; строка `ITD-RUN` без файла записи; испорченная запись; два id
в одном вызове; повтор id; вызов, в выводе которого есть строка не из прогона; зеленый другого скрипта,
с другими аргументами, в другом режиме или другим интерпретатором; зеленый вне корня проекта
или на чужом HEAD; зеленая запись при исходе сигнала не pass; более поздний красный того же вызова;
реальный провал теста. После прогона мутации нужен еще один зеленый прогон оракула из корня проекта.

Правила использования: один записанный прогон на Bash-вызов и ничего другого с выводом. Вывод можно
резать построчно (`tail -3`, `grep`), но итоговая строка оракула должна остаться: `2>&1 | tail -1`
оставит одну строку `ITD-RUN`, исход станет unknown и гашения не будет; `cut -c` меняет строки и
отвязывает запись; вывод длиннее 400 строк на поток без `tail` тоже не привяжется (в записи только
хвост). Эхо кода принимается только в форме `EXIT: N` (не длиннее трех цифр). Пустые строки не
сравниваются (хост склеивает stdout и stderr через перевод строки): команда, печатающая только пустые
строки, для гейта равна молчащей. Привязка идет по принадлежности строк, а не
по равенству вывода: чужая команда, напечатавшая ровно строку прогона, от него неотличима. Границы: команда того же вызова, которая ничего не печатает, гейту не видна ни до
фикса, ни после; переменные окружения вызова в идентичность не входят. Намеренно
подделанная запись (файл и вывод вместе) - принятый остаточный риск (владелец, 2026-10-02): гейт ловит
ошибку, а не умысел. `itd_hygiene.py close` записи не читает. Оракул -
`tests/verify_completion_supersede.py` (`--mutations`).

## Ожидаемый код чек-команды - не красный слой (COMPLETION-FALSE-RED-1, 2026-10-02)

`scripts/itd_stop_rule.py --check-binding` выходит 2, когда привязка не выровнена
или активного юнита нет, - это ответ проверки, а не провал теста. Гейт не
считает его красным слоем ровно в одной литеральной форме:

    sh skills/_shared/itd_py.sh scripts/itd_stop_rule.py --check-binding; echo "EXIT: $?"[; ...]

и только если сам скрипт доказал, что исполнился: в выводе ровно одна строка
`BINDING <STATE>` и она стоит до единственной строки `EXIT: 2`, и хук сам пересчитывает
ответ: запускает скрипт своим интерпретатором (не через `PATH` оболочки) в корне проекта и
требует тот же код и ту же строку `BINDING` (подставной `sh`/функция могут разве что повторить
правдивый ответ), в команде нет `&&`/`||` и других `$?`, а остаток вывода
без строки `EXIT` сам дает явный pass (иначе молча упавший хвост стал бы unknown), а хвост после
эха - не больше одного стейтмента: префикс никогда не делает вердикт зеленее, чем тот же хвост
отдельно. Тогда строка
`EXIT: 2` вырезается до вычисления исхода, а в сигнал пишется `expected_exit`.
Литерал сравнивается побайтно, включая разделители `; `. Любая другая форма (перевод строки
вместо `; `, другой код, редирект, префикс `cd`/переменная/обертка,
другой интерпретатор, лишний аргумент, `printf`, одинарные кавычки, нет строки
`BINDING`, хвост в строке `EXIT`) судится как до фикса. Реестр -
`DECLARED_CHECKS` в `hooks/completion_lib.py`; оракул -
`tests/verify_completion_false_red.py` (11 мутантов).

Почему так узко: широкий вариант (объявленный прогон мутации, гашение
одноразового красного поздним зеленым того же оракула) разбирал произвольный
текст shell и шесть раундов независимого ревью подряд находили в разборе новую
дыру; стоп-правило вернуло REDESIGN_OR_DISCARD. Эти два класса вынесены в юнит
COMPLETION-SUPERSEDE-1 - на доказательстве исполнения, а не на тексте команды.

## Леджер обходов и его перенос (RSI-DEBT-2, 2026-09-12)

Строка аудита `COMPLETION_BYPASS` идёт в **неотслеживаемый** append-only леджер
`.itd-memory/completion-bypass.jsonl`, а не в отслеживаемый
`.itd-memory/events.jsonl`.

Причина механическая, не стилистическая. Коммит-гейт исполняется ВНУТРИ
`git commit`. Дозапись в отслеживаемый файл в этот момент делает рабочее дерево
отличным от прореверенного кандидата, и гейт точного дерева отказывает ровно
тому коммиту, ради которого обход и был выдан. Обход при этом остаётся
обязательным к аудиту: неудачная запись по-прежнему запрещает обход
(fail-closed), а причина по-прежнему обязательна.

Запись идёт через якорный писатель `durable_append_bytes`
(`skills/_shared/itd_safe_atomic.py`): путь проверяется покомпонентно от корня
проекта, симлинк в любом звене — отказ. Подложенная по пути леджера ссылка не
перенаправит доверенную дозапись в чужой файл.

Перенос в канонический журнал — **явный шаг ledger-close**, когда дерево и так
меняется бухгалтерски:

```bash
sh skills/_shared/itd_py.sh skills/_shared/itd_bypass_audit.py carry
```

Шаг **не удаляет** леджер. Удаление и было источником потери: между снимком и
очисткой гейт может дописать новую строку обхода, а писатель, державший
дескриптор, допишет её даже в уже отвязанный inode. Ни ротация, ни наблюдение
за размером этого не закрывают — доказать, что писатель больше не допишет,
нельзя. Поэтому опасная операция убрана целиком: перенос только читает леджер и
дописывает журнал, а уже перенесённые строки отсеиваются по `id`. Потерять
строку физически нечему.

Цена — леджер растёт. Она мала: строка появляется только при осознанном обходе,
файл не отслеживается, а повторный перенос его не дублирует. `--dry-run`
показывает, сколько строк ждёт переноса.

Целью не может стать отслеживаемый путь — и это проверяется, а не
предполагается: `git ls-files --error-unmatch` отвечает трисостоятельно, и
дозапись разрешает ТОЛЬКО определённый ответ «не отслеживается» (код 1). Код 0
означает отслеживаемый файл, любой другой исход (git отсутствует, таймаут, не
репозиторий) — отказ, потому что запрет, открывающийся при сбое git, не запрет.

Путь по умолчанию объявлен в двух местах — `BYPASS_AUDIT_LEDGER` в
`hooks/completion-gate.sh` и в `docs/templates/itd/itd_hygiene.py`. Слить копии
нельзя (шаблон копируется в чужие проекты), поэтому их расхождение пинится
оракулом `tests/verify_completion_gate.py`.
